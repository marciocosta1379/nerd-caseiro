Quem tem uma casa com muitos sensores sem fio descobre um problema chato depois de alguns meses: **as baterias acabam em momentos diferentes**, e quase sempre sem aviso. O sensor da porta de entrada para de responder justamente no dia da viagem, o botão do quarto não funciona mais, o sensor de vazamento da lavanderia está morto há semanas e ninguém percebeu.

O Home Assistant sabe o nível de bateria de quase todos esses dispositivos. O que falta é juntar a informação num aviso só. Este tutorial monta uma automação que, **uma vez por dia**, verifica **todos os sensores de bateria** da casa e manda para o celular a lista dos que estão abaixo de 20%, com o nome do dispositivo, o cômodo e o percentual.

> **Base deste tutorial:** o código vem do tutorial oficial **"Low battery alerts"** da documentação do Home Assistant, conferido na versão **2026.11.1**, e da página oficial de **gatilhos de automação**. Os links estão no fim do post. O autor não testou em bancada; o procedimento é o da documentação, e os cuidados com Zigbee vêm de relatos do fórum oficial.

## O que vamos montar

O resultado é uma notificação diária como esta, no celular:

> 2 devices need new batteries: Front door lock in Hallway (15%), Motion sensor in Kitchen (12%).

Ou, quando está tudo bem:

> All batteries are healthy.

Mais abaixo, o post mostra como trocar o texto para português.

## Antes de começar

Você precisa de:

- **Home Assistant** atualizado (a documentação usada aqui é da versão 2026.11);
- pelo menos **um dispositivo com bateria** que informe o percentual ao Home Assistant;
- um serviço de **notificação no celular**, normalmente o aplicativo Home Assistant instalado. O site tem um guia sobre [notificação no celular com o app do Home Assistant](/posts/notificacao-celular-home-assistant-app/);
- acesso ao **editor de template** em **Ferramentas de desenvolvedor → Template**.

## Passo 1: veja quais sensores de bateria você tem

Em **Ferramentas de desenvolvedor → Estados**, filtre por `battery`. Aparecem as entidades com nível de bateria: sensores Zigbee, fechaduras, botões, controles e também o celular, se o aplicativo estiver instalado.

A documentação chama atenção para um detalhe: **alguns dispositivos não informam o percentual**, só um estado de "bateria baixa" como `binary_sensor`. Esses são tratados mais abaixo.

## Passo 2: liste as baterias fracas

Cole este template no **editor de template**. Ele percorre todos os sensores com `device_class` de bateria, **ignora os que estão desconhecidos ou indisponíveis** e junta numa lista os que estão abaixo de 20%:

```jinja
{% set low = namespace(batteries=[]) %}
{% for sensor in states.sensor
  | selectattr('attributes.device_class', 'eq', 'battery')
  | rejectattr('state', 'in', ['unknown', 'unavailable']) %}
  {% if sensor.state | float(100) < 20 %}
    {% set device = device_name(sensor.entity_id) or sensor.name %}
    {% set low.batteries = low.batteries + [device] %}
  {% endif %}
{% endfor %}
{{ low.batteries }}
```

O resultado aparece ao lado, como uma lista de nomes de dispositivos.

O que cada parte faz:

- `states.sensor | selectattr(...)` filtra só os sensores de **bateria**.
- `rejectattr('state', 'in', ['unknown', 'unavailable'])` descarta os que não estão informando valor.
- `float(100)` converte o estado em número; se a conversão falhar, usa 100, o que evita falso alarme.
- `device_name(...)` usa o **nome do dispositivo** em vez do nome do sensor, porque o sensor costuma se chamar só "Battery".
- O `namespace` é necessário porque, no Jinja, variáveis criadas dentro de um laço não sobrevivem fora dele. A documentação explica exatamente esse ponto.

**Dica da documentação:** se a lista vier vazia, troque temporariamente `20` por `100`. Se aparecerem nomes, o template está funcionando; é só voltar para 20.

## Passo 3: monte a mensagem

A versão completa da documentação acrescenta o **cômodo** (área) e o **percentual**, e escolhe a frase conforme a quantidade de dispositivos:

```jinja
{% set low = namespace(batteries=[]) %}
{% for sensor in states.sensor
   | selectattr('attributes.device_class', 'eq', 'battery')
   | rejectattr('state', 'in', ['unknown', 'unavailable']) %}
  {% if sensor.state | float(100) < 20 %}
    {% set device = device_name(sensor.entity_id) or sensor.name %}
    {% set area = area_name(sensor.entity_id) %}
    {% set label = device ~ (' in ' ~ area if area else '')
       ~ ' (' ~ sensor.state ~ '%)' %}
    {% set low.batteries = low.batteries + [label] %}
  {% endif %}
{% endfor %}
{% if low.batteries | count == 0 %}
  All batteries are healthy.
{% elif low.batteries | count == 1 %}
  1 device needs a new battery: {{ low.batteries[0] }}.
{% else %}
  {{ low.batteries | count }} devices need new batteries: {{
     low.batteries | join(', ') }}.
{% endif %}
```

`area_name(...)` busca o nome da área atribuída ao dispositivo, e o `~` junta pedaços de texto.

### Para receber a mensagem em português

O código acima é o da documentação, com o texto em inglês. As frases que aparecem na notificação são só texto, e podem ser trocadas sem mexer na lógica. Por exemplo, nas três últimas condições:

- `All batteries are healthy.` → `Todas as baterias estão boas.`
- `1 device needs a new battery:` → `1 dispositivo precisa de bateria nova:`
- `devices need new batteries:` → `dispositivos precisam de baterias novas:`
- `' in '` (entre o dispositivo e o cômodo) → `' na '` ou `' em '`.

Depois de trocar, confira o resultado no editor de template antes de colar na automação.

## Passo 4: crie a automação

Crie uma automação chamada, por exemplo, **"Aviso de bateria fraca"**, com:

- **Gatilho:** horário fixo, uma vez por dia (a documentação usa 09:00:00 como exemplo).
- **Ação:** notificação com o template do passo 3 como mensagem.

Em YAML, o gatilho de horário segue a sintaxe da página oficial de gatilhos:

```yaml
triggers:
  - trigger: time
    at: "09:00:00"
```

E a ação, como está no tutorial oficial:

```yaml
- action: notify.send_message
  target:
    entity_id: notify.my_device
  data:
    title: "Battery check"
    message: >
      {% set low = namespace(batteries=[]) %}
      {% for sensor in states.sensor
         | selectattr('attributes.device_class', 'eq', 'battery')
         | rejectattr('state', 'in', ['unknown', 'unavailable']) %}
        {% if sensor.state | float(100) < 20 %}
          {% set device = device_name(sensor.entity_id) or sensor.name %}
          {% set area = area_name(sensor.entity_id) %}
          {% set label = device ~ (' in ' ~ area if area else '')
             ~ ' (' ~ sensor.state ~ '%)' %}
          {% set low.batteries = low.batteries + [label] %}
        {% endif %}
      {% endfor %}
      {% if low.batteries | count == 0 %}
        All batteries are healthy.
      {% elif low.batteries | count == 1 %}
        1 device needs a new battery: {{ low.batteries[0] }}.
      {% else %}
        {{ low.batteries | count }} devices need new batteries: {{
           low.batteries | join(', ') }}.
      {% endif %}
```

Troque `notify.my_device` pelo **alvo de notificação do seu celular**. A forma mais simples de acertar o nome é montar a ação pelo editor visual da automação, que lista os alvos disponíveis.

## Passo 5: teste

Na lista de automações, use **Executar ação** para disparar a automação na hora. A notificação deve chegar ao celular. Se não chegar, a documentação orienta a:

1. conferir o **nome da ação de notificação** do seu sistema;
2. abrir o **rastreamento (trace)** da automação, que mostra em que ponto ela parou.

## Por que uma verificação diária, e não um aviso a cada sensor

Seria possível criar uma automação para cada sensor, disparando quando a bateria cair abaixo de um valor. Com cinco sensores, funciona. Com trinta, vira uma lista de automações difícil de manter, e cada sensor novo exige uma automação nova.

O template deste tutorial resolve isso de outro jeito: ele **descobre sozinho** todos os sensores de bateria da casa, inclusive os que você adicionar no futuro, desde que tenham o `device_class` de bateria. Uma automação só cuida de tudo.

O aviso diário também tem uma vantagem prática: bateria baixa não é emergência de minuto. Receber uma lista por dia, num horário em que você pode agir, é mais útil do que dez notificações espalhadas.

## Ideias para adaptar

A documentação lista algumas extensões possíveis, que dá para montar depois com calma:

- **Não mandar nada nos dias em que está tudo bem**, para a notificação só aparecer quando houver o que trocar.
- **Guardar o limite num auxiliar numérico**, para mudar de 20% para 15% pela interface, sem editar o template.
- **Mudar a frequência**, por exemplo para uma vez por semana, no domingo de manhã.
- **Listar à parte os dispositivos indisponíveis**, que podem estar com a bateria morta.
- **Ordenar do menor para o maior percentual**, para ver primeiro os mais urgentes.

Antes de mexer, teste cada mudança no editor de template: o resultado aparece na hora, sem precisar esperar a automação disparar.

## Indo além: sensores que só dizem "bateria baixa"

Alguns dispositivos não informam percentual, só um `binary_sensor` que liga quando a bateria está baixa. A documentação traz um segundo laço para incluí-los na mesma lista. Ele entra **depois do laço dos sensores numéricos e antes da formatação final**:

```jinja
{% for binary_sensor in states.binary_sensor
   | selectattr('attributes.device_class', 'eq', 'battery')
   | selectattr('state', 'eq', 'on') %}
  {% set device = device_name(binary_sensor.entity_id)
     or binary_sensor.name %}
  {% set area = area_name(binary_sensor.entity_id) %}
  {% set label = device ~ (' in ' ~ area if area else '')
     ~ ' (Low)' %}
  {% set low.batteries = low.batteries + [label] %}
{% endfor %}
```

Um `binary_sensor` de bateria no estado `on` significa bateria baixa.

## Indo além: ignorar alguns dispositivos

Para deixar de fora entidades específicas (o celular, por exemplo), a documentação sugere criar uma lista antes dos laços:

```jinja
{% set excluded_entities = [
  'sensor.garage_battery',
  'binary_sensor.attic_low_battery'
] %}
```

E acrescentar `| rejectattr('entity_id', 'in', excluded_entities)` logo depois do filtro de `device_class` em cada laço. Troque os exemplos pelos `entity_id` reais que você quer ignorar.

## O que a documentação não diz: o percentual pode enganar

Aqui entra a parte que só aparece no uso. No fórum oficial do Home Assistant, há muitos relatos sobre sensores Zigbee com bateria **CR2032** que:

- mostram **100% por meses** e depois **caem de repente** ou param de responder;
- ficam **travados num percentual** mesmo com a bateria já fraca;
- em alguns modelos, reportam o percentual **em dobro ou pela metade**, por diferença de unidade no padrão Zigbee.

A explicação mais citada é que esses sensores **calculam o percentual pela tensão**. A tensão de uma bateria de lítio tipo moeda fica quase estável durante boa parte da vida útil e despenca no fim, então o percentual não acompanha o desgaste real.

Na prática, isso significa:

1. **Não confie só no limite de 20%** para dispositivos críticos (porta de entrada, vazamento, fumaça). Considere trocar a bateria por calendário, por exemplo uma vez por ano.
2. **Acompanhe também os indisponíveis.** A própria documentação sugere tratar os dispositivos `unavailable` à parte, porque eles podem estar com a bateria morta.
3. **Anote a data da troca** de bateria de cada sensor.

## Qual bateria cada sensor usa

A bateria certa está escrita **no próprio compartimento** ou no manual. As mais comuns em casa inteligente:

| Bateria | Onde costuma aparecer |
|---|---|
| CR2032 | sensores de porta e janela, botões, sensores de temperatura e umidade |
| CR2450 | alguns sensores e botões que pedem mais autonomia |
| CR2477 | alguns sensores de porta e de movimento |
| AAA | sensores de movimento, fechaduras pequenas, controles |
| AA | fechaduras, sensores maiores, alguns hubs portáteis |

Duas dicas na hora da troca:

- **Não toque nas faces da bateria moeda com os dedos úmidos**; segure pelas bordas.
- **Guarde as baterias moeda longe de crianças.** Engolir uma bateria tipo moeda é uma emergência médica.

## Erros comuns

- **Copiar a ação sem trocar `notify.my_device`** pelo alvo real.
- **Achar que lista vazia é erro**: teste com o limite 100.
- **Confiar no percentual** de sensores Zigbee com CR2032 para dispositivos críticos.
- **Ignorar os indisponíveis**, que podem estar sem bateria.
- **Comprar CR2032 para sensor que usa CR2450**, ou o contrário.

## Resumo

- Um **template oficial** percorre todos os sensores de bateria e lista os abaixo de 20%.
- Um **gatilho de horário** dispara a verificação uma vez por dia; a **ação de notificação** manda a lista para o celular.
- Inclua os **binary_sensor de bateria** e exclua entidades que não interessam.
- O percentual de sensores com **CR2032** pode enganar: acompanhe também os **indisponíveis** e troque os críticos por calendário.
